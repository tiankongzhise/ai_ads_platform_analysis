# 教育广告 CRM 数据分析平台项目概述

## 1. 文档目的

本文档作为项目瀑布模型的第一阶段文档，用于明确项目背景、业务目标、目标用户、系统范围、核心概念和整体建设原则。后续需求规格、架构设计、数据库设计、接口设计、测试计划和部署运维文档均以本文档和根目录 `readme.md` 为主要依据。

本项目的参考材料来自 `md/` 目录，但参考材料只用于补充行业背景、用户体验思路、界面风格和任务拆分，不作为最终技术约束来源。若参考材料与 `readme.md` 冲突，以 `readme.md` 和本系列文档中的最终决策为准。

## 2. 项目背景

教育集团、学校、校区和招生团队在广告投放与招生线索管理中通常面临数据割裂问题。广告平台能看到花费、曝光、点击和表单数据，但学校真正关心的是线索是否有效、是否到校、是否报名、最终是否产生招生收入。传统做法依赖 Excel、人工汇总和事后复盘，无法及时发现投放问题，也难以处理多个团队争抢同一学生或家长咨询的归属纠纷。

本项目旨在建设一个面向教育行业的广告 CRM 数据分析平台，将组织管理、广告渠道、招生团队、线索上报、冲突裁定、广告数据同步、ETL 标准化、BI 分析和报表输出串联成闭环，让管理者能够按小时了解招生进度、广告消耗、团队效率和渠道 ROI。

## 3. 项目目标

项目的总体目标是为教育集团和学校提供一套可持续演进的广告招生数据中台与 BI 应用：

- 支持集团、区域、学校、校区等多级组织结构。
- 支持各级组织配置招生团队和广告渠道。
- 支持团队通过 Excel 或 API 上报线索。
- 支持系统识别同手机号线索冲突，并提供归属裁定依据。
- 支持按小时聚合广告结果、线索结果和招生进度。
- 支持抖音、腾讯、百度、小红书等平台数据接入，并保留平台报表差异。
- 支持教育行业标准 BI 模板、付费用户可配置 BI 和租户定制 BI 扩展。
- 支持虚拟演示账户，通过临时 OAuth2 接入广告数据进行现场演示，并在生命周期结束后彻底清理业务数据。

## 4. 目标用户

### 4.1 教育集团管理层

关注集团整体招生进度、各学校表现、广告预算使用效率、团队转化能力和最终 ROI。需要跨组织汇总、横向对比和趋势分析。

### 4.2 学校与校区负责人

关注本校区招生团队是否按预算投放广告、各渠道线索是否有效、报名结果如何、是否存在多团队重复跟进和归属争议。

### 4.3 招生团队主管

关注团队线索上报、跟进阶段、到校、报名和成交表现。需要查看团队效率、冲突线索和归属结果。

### 4.4 市场投放人员

关注抖音、腾讯、百度、小红书等广告平台的花费、线索成本、报名成本、ROI 和广告计划表现。需要及时调整预算和投放策略。

### 4.5 销售与实施人员

需要使用虚拟演示账户在客户现场快速接入广告数据，展示平台能力，同时保证演示数据可销毁、可审计、可迁移。

## 5. 系统范围

### 5.1 范围内

- 多租户组织与子组织管理。
- 招生团队与广告渠道配置。
- 线索 Excel 上传与 API 上报。
- 线索唯一 ID 生成、团队内去重、跨团队冲突识别。
- 基于上报时间、首次到校、首次报名等规则的归属裁定。
- 广告平台数据同步基座与平台适配模块。
- 原始广告报表和平台差异字段的 `jsonb` 存储。
- ETL 层标准化、指标计算和数据集生成。
- 教育行业标准 BI 模板。
- 付费用户受控 BI 配置。
- 租户定制 BI 扩展包。
- 报表生成、导出和行动建议。
- 虚拟演示账户生命周期、清理和迁移。
- Redis 缓存、幂等控制和短期状态。
- PGMQ 消息队列与异步任务。

### 5.2 范围外

- 重新开发鉴权系统。鉴权能力已完成，本项目只定义接入边界。
- 重新开发广告平台 OAuth 回调。回调能力已完成，本项目只定义回调后的数据接入与任务触发。
- 允许客户直接编写 SQL 或上传任意代码。
- 在第一阶段实现自动投放优化、素材生成或完整 AI 投放托管。
- 将所有广告平台字段强行统一为单一表结构。平台差异先进入原始 `jsonb`，后续通过 ETL 解决。

## 6. 建设原则

### 6.1 README 优先

技术栈、系统边界和业务约束以 `readme.md` 为准。参考文档中出现的 MySQL、Celery、模块化单体等旧方案不进入最终架构。

### 6.2 微服务模块化

系统采用微服务模块化开发。服务边界围绕业务能力划分，每个服务可独立部署、测试、扩容和灰度发布。

### 6.3 Go 与 Python 分工

Go 负责轻量、高并发、配置类和控制面模块，包括组织、团队、渠道、权限校验、配置 CRUD、健康检查、BI 元数据、回调接入协调。

Python 负责复杂业务和数据处理模块，包括 Excel 解析、广告数据同步适配、ETL、归因分析、冲突分析、BI 指标、报表生成。

### 6.4 原始数据先保真，标准化后置

各平台报表存在不同字段、口径和拉取规则。系统先将原始数据以 `jsonb` 和元数据方式存储，确保可追溯，再通过 ETL 层产出标准事实表、维度表和 BI 数据集。

### 6.5 用户 BI 受控配置

普通用户和付费用户均不允许直接写 SQL。BI 配置基于指标目录、维度目录、数据集目录、图表注册表和权限规则完成。

### 6.6 数据生命周期明确

正式租户数据、虚拟演示账户数据、缓存、导入文件、OAuth token、队列消息和清理审计必须有清晰生命周期。虚拟账户销毁后不得保留客户业务数据。

## 7. 核心业务对象

| 术语 | 说明 |
| --- | --- |
| 租户 | 一个正式教育集团、学校客户或一个虚拟演示账户的数据隔离单元。 |
| 组织 | 租户下的集团、区域、学校、校区等树形节点。 |
| 子组织 | 组织树中的下级节点，可继续拥有团队、渠道和子组织。 |
| 招生团队 | 隶属于某组织，负责投放、跟进或上报线索的团队。 |
| 广告渠道 | 抖音、腾讯、百度、小红书等广告平台或平台内账户。 |
| 线索 | 学生或家长咨询记录，由系统生成唯一线索 ID。 |
| 冲突线索 | 不同团队上报相同手机号或同一潜在客户时形成的冲突记录。 |
| 主咨询 | 管理者裁定后被认定为主要归属的咨询记录。 |
| 冲突量 | 非主咨询的重复咨询记录，用于统计和限制无效跟进。 |
| 原始报表 | 广告平台返回的未经标准化的报表数据。 |
| ETL | 将原始报表和业务数据抽取、转换、加载为标准指标和数据集的处理层。 |
| 指标目录 | 平台允许 BI 使用的指标定义集合。 |
| 维度目录 | 平台允许 BI 使用的分析维度集合。 |
| 数据集目录 | BI 可访问的受控数据集定义。 |
| 虚拟演示账户 | 现场演示用的临时账户，最长有效期 7 天，可销毁或授权迁移。 |

## 8. 成功标准

- 管理者能够按组织层级查看招生进度、广告消耗、线索数量、报名结果和 ROI。
- 学校能够及时发现团队是否投放广告、投放效果如何。
- 多团队重复咨询能够被系统识别，并进入可审计的归属裁定流程。
- 广告平台原始数据能完整存储并可追溯，ETL 后能支持多报表、多指标和多租户 BI。
- 虚拟演示账户能安全接入、限期保留、可授权迁移、可彻底清理。
- 服务可以按模块独立部署、独立测试和逐步替换实现。
