# 教育广告 CRM 数据分析平台可行性分析

## 1. 文档目的

本文档用于评估教育广告 CRM 数据分析平台在业务、技术、经济、运营和风险方面的可行性，为后续需求规格和架构设计提供决策依据。

## 2. 业务可行性

### 2.1 需求真实性

教育行业招生链路天然包含广告投放、线索收集、咨询跟进、到校、报名和成交等环节。现有数据通常分散在广告平台、Excel、团队台账和 CRM 中，导致管理层无法及时判断预算是否有效，也无法在冲突线索发生时快速裁定归属。

README 中列出的痛点具有明确业务闭环：

- 集团无法及时掌握各学校招生进度。
- 学校无法及时确认团队是否投放广告以及效果如何。
- 多团队重复获取同一学生或家长咨询，导致归属争议。
- 渠道好坏通常只能在事后总结，无法及时优化投放。

系统通过组织层级、渠道接入、团队线索、冲突裁定、小时聚合和 BI 分析解决这些问题，因此业务链路完整且需求成立。

### 2.2 用户付费动机

平台直接关联广告成本和招生收入，能够用 ROI、线索成本、报名成本、冲突线索占比等指标呈现价值。相较通用 CRM 或单一广告后台，本项目的付费动机来自三个方面：

- 降低无效广告支出。
- 提升团队跟进效率。
- 减少线索归属纠纷和管理寻租空间。

### 2.3 行业切入合理性

教育行业适合作为首个垂直行业，原因如下：

- 招生过程有相对稳定的漏斗阶段。
- 广告渠道集中在抖音、腾讯、百度、小红书等主流平台。
- 学校、校区、团队的组织结构适合树形建模。
- Excel 线索台账仍普遍存在，低门槛导入价值明显。
- 招生结果和广告花费能形成可量化 ROI。

## 3. 技术可行性

### 3.1 架构可行性

系统采用前后端分离和微服务模块化架构。该架构适合本项目的原因：

- 广告同步、Excel 解析、ETL、BI 计算属于异步和计算密集任务，可独立扩容。
- 组织、团队、渠道、配置 CRUD 属于稳定控制面，可由 Go 服务高效承载。
- Python 生态适合数据处理、报表生成和复杂规则计算。
- PostgreSQL 支持关系模型、递归组织树、事务、索引、`jsonb` 和分析型扩展能力。
- Redis 能支撑缓存、短期状态、OAuth 临时状态、幂等锁和热点 BI。
- PGMQ 能在 PostgreSQL 体系内提供队列能力，降低早期基础设施复杂度。

### 3.2 数据模型可行性

系统需要同时处理强结构数据和弱结构数据。PostgreSQL 能满足两类需求：

- 强结构数据：租户、组织、团队、线索、冲突、归属裁定、BI 元数据。
- 弱结构数据：广告平台原始报表、平台字段差异、同步上下文、回调载荷、扩展配置。

使用 `jsonb` 保存平台原始数据，可避免过早统一平台字段导致数据丢失。ETL 层再产出标准事实表和维度表，可兼顾保真与分析效率。

### 3.3 消息队列可行性

PGMQ 适合本项目第一阶段：

- 与 PostgreSQL 部署体系一致，减少 RabbitMQ、Kafka 等额外组件运维成本。
- 支持队列消息、可见性超时和重试机制。
- 适合线索上报、广告同步、小时聚合、BI 刷新、报表生成、虚拟账户清理等任务。

若后期任务量显著增长，可将热点队列迁移到 Kafka、RabbitMQ 或云消息队列，PGMQ 保留为业务内建队列或轻量任务队列。

### 3.4 已有能力接入可行性

鉴权和广告平台回调已完成开发。本项目不重复建设这些能力，只需要定义：

- 调用鉴权服务获取用户、租户、角色和组织范围。
- 广告平台 OAuth 回调完成后如何创建平台账户、触发同步任务和记录同步状态。
- 已完成回调能力与广告数据基座模块之间的接口契约。

## 4. 经济可行性

### 4.1 开发成本可控

项目采用成熟技术栈：

- 前端：React、TypeScript、Vite、Ant Design Pro、ECharts。
- 后端：Go、Python。
- 数据库：PostgreSQL。
- 缓存：Redis。
- 队列：PGMQ。

这些技术生态成熟，人员招聘和后续维护成本相对可控。微服务边界按业务模块拆分，允许逐步实现，不要求一次性完成全部能力。

### 4.2 运维成本可控

第一阶段核心基础设施只有 PostgreSQL、Redis、对象存储、服务容器和反向代理。PGMQ 依附 PostgreSQL，避免额外 MQ 集群。对于 MVP 和早期正式版，运维复杂度可控。

### 4.3 收益路径清晰

平台可以通过以下方式变现：

- SaaS 订阅费。
- 付费 BI 配置能力。
- 租户定制 BI 扩展包。
- 数据分析与实施服务。
- 面向教育集团的多校区管理套餐。

由于平台指标直接指向广告成本与招生收入，销售论证更容易量化。

## 5. 运营可行性

### 5.1 实施路径

建议按低门槛接入路径运营：

1. 创建正式租户或虚拟演示账户。
2. 接入广告账户或使用演示数据。
3. 上传 Excel 线索或通过 API 上报。
4. 系统完成冲突识别、归因和小时聚合。
5. 用户查看标准 BI 模板。
6. 付费用户配置看板或购买定制 BI。

### 5.2 客户成功要点

- 首次使用必须避免空仪表盘。
- 引导用户完成广告账户接入和线索导入。
- 对字段映射、归因规则和冲突裁定提供清晰说明。
- 报表不仅提供数据，还应提供行动建议。

### 5.3 支持与实施

平台需要准备：

- Excel 标准模板。
- 广告平台授权操作指南。
- 常见字段映射词库。
- 冲突裁定规则说明。
- BI 指标口径说明。
- 虚拟演示账户清理与迁移说明。

## 6. 风险分析

| 风险 | 影响 | 概率 | 应对策略 |
| --- | --- | --- | --- |
| 广告平台 API 规则差异大 | 同步和报表稳定性受影响 | 高 | 建设平台数据获取基座，原始数据 `jsonb` 保真，平台适配独立版本管理。 |
| 平台 API 审批或限流 | 接入周期延迟 | 中 | 提供 Mock 与虚拟演示数据，限制同步频率，设计重试和告警。 |
| Excel 格式差异大 | 导入失败率上升 | 高 | Python 导入服务支持字段映射、预览、错误报告和模板下载。 |
| 多租户数据泄露 | 严重安全事故 | 低 | 所有核心表带 `tenant_id`，服务层强制租户上下文，测试覆盖隔离。 |
| 线索冲突裁定引发争议 | 影响客户信任 | 中 | 保留上报时间、来源、处理轨迹和裁定审计。 |
| BI 指标口径不一致 | 管理决策错误 | 中 | 指标目录版本化，报表记录指标版本和 ETL 批次。 |
| 虚拟账户清理不彻底 | 数据合规风险 | 中 | 建立清理任务、清理审计和清理验证机制。 |
| 微服务过早过细 | 增加开发协调成本 | 中 | 按业务边界模块化，先确保核心闭环，服务拆分保持最小必要粒度。 |

## 7. 关键成功条件

- 广告数据接入与线索上报链路必须稳定。
- 组织树、团队、渠道和线索归属模型必须清晰。
- 冲突识别和裁定流程必须可解释、可审计。
- BI 指标口径必须版本化并可追溯。
- 原始数据与 ETL 标准数据必须同时保留。
- 虚拟演示账户必须在数据安全上可信。
- 微服务边界必须支持独立部署和逐步替换。

## 8. 结论

本项目在业务、技术、经济和运营层面均具备可行性。推荐采用“先打通教育行业招生广告数据闭环，再扩展平台和 BI 定制能力”的实施路径。第一阶段应优先完成组织树、广告数据基座、线索上报、冲突裁定、ETL、标准 BI 和虚拟账户生命周期能力。
