# 教育广告 CRM 数据分析平台需求规格说明书

## 1. 文档目的

本文档定义教育广告 CRM 数据分析平台的功能需求、非功能需求、数据需求和约束条件。本文档是后续系统架构、数据库设计、API 设计、模块设计、测试计划和项目计划的主要输入。

## 2. 总体需求

系统应支持教育集团、学校、校区和招生团队围绕广告投放与招生线索形成数据闭环。系统需要接入多广告平台数据，接收团队线索上报，识别重复咨询和线索冲突，按组织层级聚合广告与招生成果，并向用户提供标准 BI、受控 BI 配置和租户定制 BI。

## 3. 用户与角色

| 角色 | 主要权限 |
| --- | --- |
| 租户管理员 | 管理租户、组织、用户、角色、BI 套餐、虚拟账户迁移授权。 |
| 集团管理者 | 查看集团及下级组织汇总数据、学校对比、渠道 ROI、报表。 |
| 学校管理者 | 管理本学校组织、团队、渠道、线索冲突和归属裁定。 |
| 团队主管 | 查看团队线索、冲突状态、跟进效率和团队报表。 |
| 招生人员 | 上报线索、查看自己负责的线索和处理状态。 |
| 市场投放人员 | 管理广告账户、查看广告同步状态、分析渠道和广告计划表现。 |
| 实施/销售人员 | 创建虚拟演示账户、发起临时授权、销毁或迁移演示数据。 |
| 平台开发人员 | 开发和发布租户 BI 扩展包、迁移脚本和定制图表。 |

## 4. 功能需求

### 4.1 租户与组织管理

- 系统应支持一个教育集团注册为一个租户。
- 租户下应支持多级组织树，包括集团、区域、学校、校区等节点。
- 任一组织节点可继续创建子组织。
- 组织节点应支持启用、停用、重命名、调整父级和查看下级汇总数据。
- 组织层级应作为权限范围、数据归集范围和 BI 筛选维度。

### 4.2 团队管理

- 每个组织可配置多个招生团队。
- 团队应关联组织、负责人、成员、可使用渠道和有效状态。
- 团队可通过 Excel 或 API 上报线索。
- 团队维度应支持线索数、有效线索、到校、报名、成交金额、转化率和冲突量统计。

### 4.3 广告渠道与账户管理

- 每个组织可配置多个广告渠道。
- 首批平台按抖音、腾讯、百度、小红书建模。
- 系统应接入已完成的广告平台 OAuth 回调能力。
- 授权完成后，系统应创建或更新广告账户引用，并触发广告数据同步任务。
- 系统应展示账户状态、最近同步时间、同步结果、错误信息和可重试操作。

### 4.4 广告数据获取基座

每个平台应建设独立的数据获取基座模块，统一包含：

- 账户引用与平台标识。
- 同步任务调度。
- 平台 API 请求封装。
- 限流、重试和错误分类。
- 原始报表数据入库。
- 同步状态记录。
- 平台特有报表规则配置。

平台差异不得在原始入库阶段被强行抹平。系统应优先保存平台原始返回数据和同步上下文，再通过 ETL 标准化。

### 4.5 线索上报

- 系统应支持 Excel 上传线索。
- 系统应支持 API 上报线索。
- 每条线索由系统生成唯一线索 ID。
- 线索至少包含租户、组织、团队、手机号哈希、上报时间、来源渠道、业务阶段和原始字段。
- 团队内不允许重复上传电话号码相同的线索。
- 不同团队上传相同电话号码时不得直接拒绝，应进入冲突识别和归属裁定流程。
- 线索原始上传字段应保存在 `jsonb` 元数据中。

### 4.6 线索冲突识别

- 系统应按手机号标准化结果识别跨团队重复咨询。
- 系统应创建冲突组，关联所有相关线索。
- 系统应支持将某条咨询标记为主咨询。
- 非主咨询应自动标记为冲突量。
- 系统应支持按冲突来源、团队、组织、处理状态和处理时长统计冲突。
- 冲突处理过程必须记录审计日志。

### 4.7 归属裁定

系统应支持至少以下归属规则：

- 首次线索上报归属。
- 首次到校归属。
- 首次报名归属。
- 管理者手动裁定归属。

归属裁定结果应记录规则类型、裁定依据、裁定人、裁定时间和说明。BI 指标计算应能够选择或展示不同归属规则下的结果。

### 4.8 小时聚合

- 系统每小时聚合广告结果和团队线索结果。
- 聚合结果应按租户、组织层级、团队、渠道、平台、课程、阶段和时间维度归集。
- 聚合任务应通过 PGMQ 触发或调度。
- 聚合结果应写入标准事实表或 BI 缓存表，并将热点结果写入 Redis。

### 4.9 标准教育 BI 模板

系统默认应提供以下 BI 场景：

- 集团总览。
- 学校对比。
- 团队效率。
- 渠道 ROI。
- 招生漏斗。
- 线索冲突。
- 归属裁定。
- 小时趋势。

默认指标至少包括：

- 广告消耗。
- 线索数。
- 有效线索数。
- 到校数。
- 报名数。
- 成交金额。
- 线索成本。
- 到校成本。
- 报名成本。
- ROI。
- 转化率。
- 冲突线索数。
- 主咨询占比。

### 4.10 付费用户 BI 配置

付费用户可通过界面配置受控 BI 能力：

- 启用或隐藏默认指标。
- 调整图表类型。
- 调整图表位置、大小和看板布局。
- 保存多个看板视图。
- 配置受控筛选条件。

用户不能直接编写 SQL。所有配置必须基于指标目录、维度目录、数据集目录和图表注册表。

### 4.11 租户定制 BI 扩展

系统应支持平台开发人员为租户交付定制 BI 扩展包。扩展包至少包含：

- 指标定义。
- 数据集定义。
- 图表定义。
- 布局模板。
- 权限要求。
- 迁移说明。
- 测试用例。

扩展包应支持按租户启用、禁用、升级和回滚。

### 4.12 报表能力

- 系统应支持多种报表获取。
- 报表应可按组织、团队、渠道、平台、课程、时间范围和归属规则生成。
- 报表生成优先由 Python 服务实现。
- 报表结果应记录生成参数、数据版本、指标版本和生成状态。
- 报表应支持下载和权限控制。

### 4.13 虚拟演示账户

- 系统应支持虚拟演示账户。
- 虚拟账户用于现场演示，不等同于正式租户账户。
- 用户可通过 OAuth2 将广告数据临时接入虚拟账户。
- 虚拟账户最长有效期为 7 天。
- 用户可随时手动销毁虚拟账户。
- 虚拟账户到期后系统自动删除。
- 销毁后业务数据、OAuth token、导入文件、缓存和队列残留必须被清理。
- 系统仅允许保留不含业务数据的系统级删除结果记录。
- 若客户开通正式账户且明确授权保留演示数据，虚拟账户数据可在有效期内迁移到正式账户。
- 迁移必须记录用户授权、迁移范围、迁移结果和操作人。
- 迁移完成后原虚拟账户仍需按生命周期规则清理。

## 5. 非功能需求

### 5.1 性能

- 常用 BI 看板首屏应优先读取 Redis 热点缓存。
- 小时聚合任务应能在下一小时开始前完成。
- Excel 导入应采用异步任务处理，不阻塞 Web 请求。
- 广告同步应按平台限流规则执行。

### 5.2 可用性

- 核心查询接口应有明确错误码。
- 异步任务应可查看状态、进度、错误信息和重试次数。
- 广告同步失败、ETL 失败、报表生成失败应产生告警事件。

### 5.3 安全

- 所有业务数据必须按租户隔离。
- 所有敏感操作必须记录审计日志。
- 手机号应存储标准化哈希，展示时脱敏。
- OAuth token 应加密存储。
- 虚拟账户必须有自动清理机制。

### 5.4 可扩展性

- 广告平台接入应按平台适配模块扩展。
- BI 指标、维度、数据集和图表应可版本化扩展。
- Go 与 Python 服务应通过 API 和消息契约解耦。

### 5.5 可维护性

- 服务应提供健康检查。
- API 应生成 OpenAPI 文档。
- 消息契约应版本化。
- 数据库迁移脚本应可回滚。

## 6. 数据需求

- PostgreSQL 为主数据库。
- 广告原始报表、平台特有字段、导入原始字段和扩展配置使用 `jsonb`。
- Redis 用于缓存、短期状态、热点 BI、OAuth 临时状态、虚拟账户过期提示和幂等控制。
- PGMQ 用于异步任务队列。
- 对象存储用于保存 Excel、错误报告和导出报表文件。

## 7. 约束条件

- 必须采用前后端分离架构。
- 后端必须使用 Go 和 Python 组合。
- 前端采用 React + TypeScript + Vite + Ant Design Pro + ECharts。
- 鉴权和广告平台回调已完成，不重复建设。
- 用户不得直接写 SQL。
- 虚拟账户业务数据不得在销毁后保留。
