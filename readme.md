# 教育行业广告 CRM 数据分析平台

本项目为 `market_research_report.md` 在教育行业招生场景中的落地实现。系统聚焦教育集团、学校、招生团队、广告渠道和招生线索之间的数据闭环，帮助管理者及时掌握广告投放、线索归属、招生进度和团队效果。

## 一、项目痛点

1. 一个教育集团可能有多所学校同时招生，集团对各学校招生进度掌握迟滞。
2. 一所学校可能有多个招生团队同时招生，每个招生团队又有多个广告渠道。招生费用拨给团队后，学校无法及时知道团队是否投放广告、投放效果如何。
3. 多个招生团队可能获取到同一个学生或家长的咨询，容易造成线索冲突。学校处理纠纷缺乏可见依据，存在寻租空间，扰乱招生秩序，降低招生效率。
4. 多个招生渠道的好坏通常要到最终总结时才知道，无法及时发现规律并调整投放和跟进策略。

## 二、项目解决方案

1. 一个教育集团可以注册一个组织账号，并管理多个子组织。
2. 子组织也可以继续管理自己的子组织，形成集团、区域、学校、校区等多级组织结构。
3. 每个子组织都可以管理多个广告投放渠道，如抖音、腾讯、百度、小红书等。
4. 每个子组织都可以配置多个招生团队。
5. 每个团队都可以上报线索。
6. 学校可以根据团队线索上报时间确定线索归属，也可以按线索业务进度确认招生结果归属，例如第一次到校、第一次报名等。
7. 当家长或学生发生多头咨询时，组织管理者可以及时选定一个主咨询，其他咨询自动标记为冲突量，避免其他团队继续浪费精力跟进。
8. 系统每小时聚合广告结果和各团队线索结果，实时展现招生进度，并按组织层级逐层归集。
9. 线索可以通过 Excel 上传，也可以通过 API 上报。
10. 上报线索由系统生成唯一线索 ID。每个团队不允许重复上传电话号码相同的线索；不同团队上传相同电话号码时不被直接拒绝，而是进入冲突识别和归属裁定流程。

## 三、技术与架构约束

1. 系统采用前后端分离架构。
2. 后端采用 Go 和 Python 组合开发：
   - Go 负责组织、团队、渠道、权限校验、配置类 CRUD、健康检查等轻量高并发模块。
   - Python 负责 Excel 解析、广告数据聚合、归因分析、冲突分析、BI 指标计算、报表生成等复杂业务模块。
3. 前端采用 React + TypeScript + Vite + Ant Design Pro + ECharts，优先满足教育集团中后台管理、BI 分析和现场演示需求。
4. 主数据库使用 PostgreSQL。
5. Redis 用于缓存、短期状态、热点 BI 数据、OAuth 临时状态、虚拟账户过期提示和幂等控制。
6. PGMQ 作为消息队列，用于线索上报、广告数据同步、小时聚合、BI 指标刷新、虚拟账户清理和迁移等异步任务。
7. 鉴权和广告平台回调已经完成开发，后续设计以接入既有能力为前提，不重复建设。
8. 整体项目采用微服务模块化开发，方便独立部署、测试和逐步演进。

## 四、BI 分析与扩展能力

系统前端需要提供教育行业通用 BI 模板，并支持付费用户进行有限配置和定制化开发服务。普通用户不允许直接编写 SQL，但平台必须为后续开发人员提供足够清晰、可控、可版本化的 BI 扩展机制。

### 4.1 标准教育 BI 模板

默认 BI 模板至少覆盖以下分析场景：

1. 集团总览：集团整体招生进度、广告消耗、线索数量、报名结果和 ROI。
2. 学校对比：不同学校、校区或子组织之间的招生效果对比。
3. 团队效率：各招生团队线索上报、有效线索、到校、报名、成交效率对比。
4. 渠道 ROI：抖音、腾讯、百度、小红书等广告渠道的消耗、线索成本、报名成本和 ROI。
5. 招生漏斗：线索、有效沟通、到校、报名、成交等阶段转化率。
6. 线索冲突：冲突线索数量、冲突来源、主咨询选择结果、冲突处理效率。
7. 归属裁定：按首次上报、首次到校、首次报名等规则形成的招生归属结果。
8. 小时趋势：广告投放、线索上报、到校和报名结果的小时级趋势。

默认指标包括广告消耗、线索数、有效线索数、到校数、报名数、成交金额、线索成本、到校成本、报名成本、ROI、转化率、冲突线索数、主咨询占比等。

### 4.2 付费用户 BI 配置能力

额外付费用户可以通过界面配置一部分 BI 能力：

1. 选择启用或隐藏默认指标。
2. 调整图表类型，例如指标卡、趋势图、柱状图、排行表、漏斗图、热力图、交叉分析表。
3. 调整图表位置、大小和看板布局。
4. 保存多个看板视图，例如集团视图、校区视图、市场负责人视图、团队主管视图。
5. 配置受控筛选条件，例如组织、学校、团队、渠道、课程、招生阶段、时间范围。

用户侧配置能力必须基于平台提供的指标目录、维度目录、数据集目录和图表注册表，不允许用户直接写 SQL。

### 4.3 定制化 BI 开发服务

平台需要支持面向不同教育集团的定制化 BI 开发服务。定制能力由平台开发人员交付，不允许客户上传任意代码。

每个租户 BI 扩展包至少包含：

1. 指标定义：定制指标名称、口径、适用租户、依赖数据集、计算方式和版本号。
2. 数据集定义：标准数据集或客户专属数据集的字段、维度和数据来源。
3. 图表定义：专属图表组件、图表配置、交互方式和默认展示规则。
4. 布局模板：客户专属看板布局、角色视图和默认筛选。
5. 权限要求：哪些角色、组织层级、套餐可以访问。
6. 迁移说明：需要执行的 PostgreSQL 迁移脚本、数据回填任务和回滚方案。
7. 测试用例：指标口径、租户隔离、权限、性能和回归测试。

定制扩展必须支持按租户启用、禁用、升级和回滚。复杂指标、预测分析、归因模型和报表生成优先由 Python 扩展包实现；轻量配置、元数据、权限校验和看板 CRUD 优先由 Go 服务实现；前端通过受控组件注册机制加载专属图表和筛选器。

## 五、虚拟演示账户

系统需要支持虚拟演示账户，方便销售或实施人员在客户现场通过 OAuth2 将广告数据临时接入平台进行演示。

1. 虚拟账户用于现场演示，不等同于正式租户账户。
2. 用户可以通过平台 OAuth2 授权将广告数据临时接入虚拟账户。
3. 虚拟账户有效期最长 7 天。
4. 用户可以在任意时间手动销毁虚拟账户。
5. 虚拟账户到期后系统自动删除。
6. 虚拟账户销毁后，业务数据、OAuth token、导入文件、缓存和队列残留都必须被清理，不保留客户业务数据。
7. 系统只允许保留不含业务数据的系统级删除结果记录，用于审计清理动作是否完成。
8. 如果客户开通正式账户，并且明确授权保留演示数据，则虚拟账户中的数据可以迁移到正式账户。
9. 数据迁移必须发生在虚拟账户有效期内，并记录用户授权、迁移范围、迁移结果和操作人。
10. 迁移完成后，原虚拟账户仍需按虚拟账户生命周期规则清理。
